# MLOPS_Innovative — Student Performance Prediction

Part of the project **"Automated MLOps Pipeline for Student Performance Prediction
with Data Drift Detection and Continuous Retraining."**

Implemented phase by phase:

- **Phase 1 (done):** core ML pipeline — synthetic data, preprocessing, Random Forest training, evaluation, single-student prediction.
- **Phase 2 (done):** MLflow experiment tracking & model versioning (local, no cloud).

> FastAPI, Docker, Evidently, Streamlit, GitHub Actions and automated retraining are **not** implemented yet — those belong to later phases.

## Problem

Predict whether a student will **PASS** or **FAIL** based on study habits and
academic indicators. This is a binary classification problem.

## Dataset

A realistic **synthetic** dataset (`data/raw/student_data.csv`) with **1000 records**
generated by `src/generate_dataset.py`. The PASS/FAIL target is produced from a
weighted combination of the features **plus random noise**, so the relationships
are realistic but not perfectly deterministic.

## Features

| Feature            | Description                        | Range        |
|--------------------|------------------------------------|--------------|
| `study_hours`      | Average study hours per day        | 0–12         |
| `attendance`       | Attendance percentage              | 30–100       |
| `previous_marks`   | Previous exam marks (%)            | 10–100       |
| `assignment_score` | Assignment score (%)               | 0–100        |
| `internal_score`   | Internal assessment score (%)      | 0–100        |
| `sleep_hours`      | Average sleep per night (hours)    | 3–11         |
| `participation`    | Class participation (0–10 scale)   | 0–10         |

**Target:** `performance` ∈ {`PASS`, `FAIL`}

## Model

`RandomForestClassifier` (scikit-learn), 200 trees, `max_depth=10`,
`min_samples_leaf=8`, with a fixed `random_state=42` for reproducibility.
Random Forest handles mixed feature scales well and needs no feature scaling.

## Phase 2 — MLflow experiment tracking & model versioning

### What is MLflow?

**MLflow** is an open-source platform for managing the machine-learning lifecycle.
Here we use two of its components:

- **Tracking** — records each training run: its parameters, metrics and artifacts
  (including the trained model), so runs can be compared over time.
- **Model Registry** — gives a trained model a name and an incrementing **version**
  number, so you can track which model is which.

### Why MLflow is used

- Every experiment is **recorded automatically** instead of being lost in the terminal.
- You can **compare runs** (e.g. different `n_estimators` or `max_depth`) side by side.
- Results are **reproducible** — parameters and metrics are stored with the model.
- The **model is versioned**, so you always know which trained model produced which metrics.

Everything runs **locally**. Tracking metadata is stored in a local **SQLite**
database (`mlflow.db`) and model artifacts in a local `mlartifacts/` folder in the
project root — no cloud account or remote server is required.

> MLflow 3.x put the old `./mlruns` file store in "maintenance mode", so this project
> uses a local SQLite backend instead. SQLite is still fully local and, unlike the file
> store, it supports the **Model Registry** — which is what makes model versioning work.

### What `train.py` logs

| Type        | Logged values                                                       |
|-------------|---------------------------------------------------------------------|
| Parameters  | `n_estimators`, `max_depth`, `min_samples_leaf`, `random_state`, `test_size` |
| Metrics     | `train_accuracy`, `accuracy`, `precision`, `recall`, `f1_score`     |
| Artifact    | The trained Random Forest model (logged via `mlflow.sklearn`)       |
| Registry    | Registered as model **`student-performance-model`** (a new version per run) |

Experiment name: **`student-performance-prediction`**.

### Commands

```bash
# 1. Install (includes MLflow)
pip install -r requirements.txt

# 2. Run training — this creates/updates the local SQLite store (mlflow.db)
python src/train.py

# 3. Start the MLflow UI (point it at the local SQLite backend), then open
#    http://127.0.0.1:5000 in your browser.
mlflow ui --backend-store-uri sqlite:///mlflow.db
# (press Ctrl+C to stop the UI)
```

> Run the `mlflow ui` command from the project root so `mlflow.db` and `mlartifacts/`
> resolve correctly. If port 5000 is busy, add `--port 5001`.

### How to view experiments

1. Start the UI with the command above and open <http://127.0.0.1:5000>.
2. In the left sidebar, click the **`student-performance-prediction`** experiment.
3. Each **row is one training run.** Click a run to see its **Parameters**,
   **Metrics**, and the **Artifacts** tab (which contains the logged `model/`).
4. Select two or more runs and click **Compare** to see them side by side.

### How model versions are represented

- Open the **Models** tab in the MLflow UI.
- The model **`student-performance-model`** is listed. Each time you run `train.py`,
  a **new version** is created: **Version 1, Version 2, Version 3 …**
- Each version links back to the exact run (and therefore the parameters and metrics)
  that produced it.
- If the local file store on your MLflow build does not support the registry, the
  model is still logged as a **run artifact** (visible under a run's *Artifacts* tab),
  and `train.py` prints a note saying so.

## Notes

- All paths are resolved relative to the project root — no hard-coded absolute paths.
- Missing dataset / model files raise a clear, actionable error message.
- All random operations use `random_state=42` for reproducible results.
- Phase 1 scripts (`evaluate.py`, `predict.py`) are unchanged and still read the
  `.pkl` model, so the core pipeline works with or without the MLflow UI running.
